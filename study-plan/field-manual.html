Capstone — Portfolio + 2 Test Strategy documents (7h)

By now ai-qa-portfolio holds P1–P6. The capstone is the actual deliverable this whole plan points at.

Most organizations shipping an AI chatbot or agent genuinely don't have a Test Strategy for it — not because the work is impossible, but because AI testing is new enough that no established template has become "the obvious thing you write" the way it already is for web/API products. That gap is your opportunity: a well-structured one, backed by your own P1-P6 evidence, is a rare and credible artifact.

What a good AI Test Strategy contains, section by section

  1. Scope — product surface, which risk categories apply, what's explicitly out of scope.
  2. Evaluation approach & metrics, and why — which metrics map to which real failure modes found in error analysis (M6).
  3. Golden dataset strategy — how built (M6), how maintained, who owns adding cases.
  4. Regression strategy — the capability-vs-regression split (M10), what triggers a new test.
  5. Safety/red-team plan — OWASP-mapped findings (M8), workflow & cadence, guardrails, risk-tiered HITL.
  6. CI/CD and reporting — how the suite runs (M10), what blocks a merge, how results reach non-engineers.
  7. Release engineering and production observability — your canary/rollback plan and gate thresholds (M11, P6), which observability stack catches drift after launch (Appendix D), and which reliability practices are planned vs. already in place.

Turn P1-P6 into cited evidence, not decoration: every claim should point at something you actually built and ran — "we validate retrieval quality with context precision/recall" should link to P1's actual test file and a real run's report. "We roll out model changes safely" should cite P6's actual canary gate thresholds.

🧠 A Test Strategy without cited evidence is a wish list; every section header should be answerable with "...and here's the file that proves it."

Test Strategy — Chatbot product

  • Scope: functional / non-functional / responsible-AI
  • Metrics chosen, and why
  • Golden-dataset approach
  • Regression strategy
  • Guardrail / red-team plan
  • CI/CD + release engineering + observability

Test Strategy — AI Agent product

  • Same shape, structured around the AI-Native Test Pyramid
  • Tool-level → tool-calling → orchestration → e2e
  • State-management / loop-detection risks

Draft both with Opus 5 — reasoning-heavy, high-stakes writing. Cite your own P1–P6 projects as evidence/appendices: that is what makes this a real strategy document, and your strongest interview artifact.

Career visibility (light-touch): as each module/project lands, update LinkedIn/resume with the specific keywords it taught you (prompt engineering, LLM-as-a-judge, red teaming, OWASP LLM Top 10, hallucination detection, token/cost consumption, RAG evaluation). A short, specific post about one real thing you built beats a generic "excited to share" post — and it's evidence, not just self-promotion.

      Homework-style extension once you've used DeepEval: spend one session evaluating Agenta against it on the same test cases, and note where each tool's approach differs — that comparison is exactly the "consulting mindset" question interviewers ask.

      Two categories, not one list: development platforms (Langfuse, LangSmith, Opik) bundle observability with evals/prompt-management/session-replay; gateway/telemetry tools (Helicone, Phoenix, Arize AX, SigNoz) focus on traces/metrics and often double as an API gateway. Pick based on which question you need answered, not which has the most features.
